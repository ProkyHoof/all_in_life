
# Day 01  
## 1 第一题：为什么要用虚拟环境？

> 假设我同时开发两个项目。项目 A 用 `openai==1.0`，项目 B 用 `openai==2.0`。如果不隔离，两个项目共用一个 Python 环境，装 1.0 的时候 B 跑不了，装 2.0 的时候 A 跑不了。虚拟环境让每个项目有独立的依赖空间，互不干扰。  
> 另外，虚拟环境还方便复现。我用 `pip freeze > requirements.txt` 锁定版本，别人拿到项目后 `pip install -r requirements.txt`，就能装出一模一样的环境。

**面试官想听到的关键词**：依赖冲突、版本隔离、可复现、requirements.txt。  
## 2 第二题：为什么 API Key 不能写在代码里？

> API Key 相当于账号密码，硬编码在代码里有三个风险：  
> 第一，推到 GitHub 后任何人可见，别人可以盗刷你的额度。  
> 第二，Git 历史会永久保留，即使后来删掉文件，历史记录里还能查到。  
> 第三，团队协作时，每个人用自己的 Key，硬编码意味着所有人共用一个 Key，无法追溯谁用了多少。  
> 
> 所以我的做法是：本地用 `.env` 文件存 Key，`.gitignore` 排除 `.env`，代码里用 `os.environ.get()` 读取。同时提供 `.env.example` 作为模板，告诉别人需要配哪些变量，但不含真实值。  

**面试官想听到的关键词**：`.env`、`.gitignore`、`os.environ`、`.env.example`、Git 历史泄露风险。  
## 3 第三题：为什么先跑 `test_api.py` 再写 NL 2 SQL？  

> 这叫**最小验证**。工程上有一个原则：**先跑通最小的闭环，再逐步加复杂度。**  
> 如果直接写 NL 2 SQL，可能同时引入三个变量：Key 有没有配好、网络能不能通、SDK 会不会用、Prompt 写没写对。一旦报错，你分不清是哪个环节的问题。  
> 先用 `test_api.py` 只验证“Key + 网络 + SDK”这一条链路，排除掉基础问题。之后写 NL 2 SQL 时如果出错，就能确定问题出在 Prompt 或 SQL 逻辑上，而不是环境。    
> 这在 Agent 开发里尤其重要。Agent 的链路很长，有模型调用、工具执行、结果解析、重试循环。如果不逐段验证，调试会非常痛苦。  

**面试官想听到的关键词**：最小验证、最小闭环、控制变量、逐段调试。  
## 4 为什么用 SQLite 而不是 MySQL？  

> SQLite 和 MySQL 的定位不同。MySQL 是**客户端-服务器**架构，需要单独安装、启动服务、配置用户权限，适合多用户并发访问的生产环境。SQLite 是**嵌入式**数据库，整个数据库就是一个文件，不需要服务进程，程序直接读写文件。    
   选 SQLite 的原因有三个：  
   第一，**学习阶段降低复杂度**。我不需要分心去配 MySQL 服务、管理用户权限，可以把精力集中在 Agent 逻辑上。  
   第二，**方便分发**。整个项目就一个文件，别人克隆下来就能跑，不需要额外安装数据库服务。  
   第三，**SQL 语法是通用的**。SQLite 的 `SELECT`、`JOIN`、`GROUP BY` 和 MySQL 基本一致。以后切换到 MySQL 或 PostgreSQL，只需要改连接配置，SQL 逻辑本身不用重写。  
# Day 02  
## 1 第一题：外键到底防什么？  

> 假设没有外键。`orders` 表里插入一条 `product_id=999` 的记录，但 `products` 表里根本没有 id 为 999 的商品。这条订单就成了“悬空引用”——你永远查不到它对应哪个商品。  
> 有了外键，数据库会在插入时检查：`product_id` 必须在 `products.id` 里存在。不存在就拒绝插入。这叫**引用完整性**。  
> 在 NL 2 SQL 场景里，外键还有一层意义：它告诉模型两张表怎么关联。模型看到 `orders.product_id` 指向 `products.id`，就知道生成 JOIN 时用 `ON orders.product_id = products.id`。  

**面试关键词**：引用完整性、悬空引用、JOIN 的依据。  
## 2 第二题：占位符的本质  

> 字符串拼接时，用户输入会被当成 SQL 语法的一部分。比如输入 `'; DROP TABLE products; --`，拼接后 SQL 变成 `SELECT * FROM products WHERE name = ''; DROP TABLE products; --'`，数据库会执行两条语句，表就被删了。  
> 占位符 `?` 的本质是：**SQL 语句的结构先被数据库编译好，值再单独传入**。值永远只是“值”，不会被解析成 SQL 语法。所以即使输入里有分号、引号，也只当普通字符处理。

**面试关键词**：参数化查询、语句预编译、值不参与语法解析。  
## 3 第三题：表多了怎么办？  
### 3.1 为什么不能把全部 Schema 塞进 Prompt？  
先算一笔账。一张表平均 10 个字段，每个字段名加类型大约 20 个 token。一张表就是 200 token。500 张表就是 **10 万 token**。  
问题一：**Token 有限**。DeepSeek 的上下文窗口虽然大，但每多一个 token 就多一份钱，而且响应变慢。  
问题二：**干扰模型**。模型看到 500 张表，你问“价格超过 5000 的产品”，它要在一堆无关的表里找 `products`，容易找错，也容易把不相关的表 JOIN 进来。  
问题三：**大部分表根本无关**。用户问商品价格，可能只需要 `products` 一张表。其他 499 张表都是噪音。  
### 3.2 解决方案：只给模型“相关的” Schema  
核心思路是：**用户问什么，就只检索和这个问题相关的表结构。** 
比如用户问“价格超过 5000 的产品”，系统先判断这个问题涉及“产品”和“价格”，然后只把 `products` 表的 Schema 塞进 Prompt。其他表不传。  
怎么判断哪些表相关？这就是 **RAG（检索增强生成）** 要做的事：  
1. 把所有表的描述、字段说明转成向量，存进向量数据库。
2. 用户提问时，把问题也转成向量。
3. 在向量数据库里找最相似的几张表。
4. 只把这几个表的 Schema 塞进 Prompt。

**面试考点**：这是 Agent 面试的**高频题**。  

> 面试官问：“你的 NL 2 SQL 怎么处理大量表？”。  
> 你答：“不能让模型看全部 Schema，Token 有限且会干扰。我用了 RAG，先对表结构和字段描述做向量化，用户提问时检索最相关的几张表，只把这几张表的 Schema 放进 Prompt。这样既省 Token，又提高准确率。”    

# Day 03  
## 1 第一题：为什么不能塞全部 Schema

> 三个原因。第一，Token 成本：500 张表可能超过 10 万 token，每次调用都烧钱。第二，干扰模型：无关表会让模型选错表、生成多余的 JOIN。第三，也是最重要的，**用户的问题通常只涉及少数几张表**。问“价格超过 5000 的产品”，只需要 `products` 一张表，其他 499 张都是噪音。  
> 所以正确做法是用 RAG 只检索相关的表结构，而不是全量塞入。  

## 2 第二题：流程要补两个细节

> 第一，**获取 Schema 的目的是什么**。不是为了“获取表”，是为了“告诉模型数据库长什么样”。模型不知道你有 `products` 还是 `goods`，必须显式告诉它。  
   第二，**重试要有上限**。你说“错误就继续调用大模型”，但如果不设上限，模型可能陷入死循环，每次生成同样的错误 SQL，无限烧钱。所以必须设 `max_retries=3`，三次还失败就返回错误。  

## 3 第三题：Agent 和普通程序的本质区别

> 普通程序是**确定性**的：输入 A，经过固定逻辑，必然得到 B。错了就抛异常。  
> Agent 是**不确定性**的：同样的输入，模型可能生成不同的 SQL。所以 Agent 必须包含“观察结果 → 判断对错 → 调整策略 → 再试”的循环。这个循环让 Agent 能处理普通程序无法处理的模糊问题，但也带来了新问题——你必须设计**评估机制**来判断它做得对不对，设计**重试上限**来防止死循环，设计**回退策略**来保证失败时不会造成破坏。  

**面试关键词**：确定性 vs 不确定性、观察-判断-调整循环、可控性设计。  

## 4 第四题：错误返回大模型的信息
完整的重试 Prompt 应该包含四样东西：  
1. 原问题
2. 表结构（Schema）
3. 失败的 SQL
4. 错误信息

## 5 思考题一：SQL 语法对但逻辑错，怎么发现？
比如用户问“最贵的商品”，模型写成 `ORDER BY price ASC`（升序，最便宜）。SQL 能执行，不报错，但结果错了。  
**怎么发现**：靠**评估**。你需要准备一批测试用例，每个都有标准答案。比如“最贵的商品”标准答案是 `MacBook Pro`，如果 Agent 返回 `Python编程书`，就判定失败。每次改 Prompt 或换模型，都跑一遍测试集，看通过率。  
这就是第三周要做的**评估体系**。面试官非常看重这个，因为大部分人只会说“我试了一下能跑”，而你能说“我有 20 个测试用例，通过率 85%”。  
## 6 思考题二：用户问隐私数据怎么办？
比如“查一下所有用户的密码”。  
**怎么处理**：三层防护。  

> 第一层，**Prompt 约束**：在 System Prompt 里明确写“只能查询商品和订单数据，不得查询用户敏感信息”。  
> 第二层，**SQL 白名单**：执行前检查 SQL，如果涉及敏感表（如 `users`），直接拒绝，不执行。  
> 第三层，**数据库权限**：给 Agent 用的数据库账号只授予 `products` 和 `orders` 的读权限，根本访问不了敏感表。  

面试关键词：Prompt 约束、SQL 校验、最小权限原则。
## 7 思考题三：字段名相似，模型选错怎么办？
比如 `price` 和 `unit_price`。  
**怎么减少**：在 Schema 里加**字段描述**。不要只给模型 `price REAL`，而是给 `price REAL -- 商品售价，含税`。模型看到描述，就知道该选哪个。  
这就是 RAG 里“字段描述向量化”的意义——不仅检索表，还检索字段的语义说明。  

# Day 04  
## 1 第一题：`get_schema` 返回的那段文本，最终去哪了。  

> 把数据库 Schema 提取成文本，作为上下文注入 Prompt。模型根据 Schema 和用户问题，生成对应的 SQL。这是 NL 2 SQL 的基础链路。  

## 2 第二题：`SQLOutput` 这个类的作用是什么，没有它会怎么样。  

> `SQLOutput` 是数据校验层。它确保模型返回的 JSON 包含 `sql` 和 `explanation` 两个字段，且类型正确。没有它，代码可能拿到不完整或类型错误的数据，在后面执行时崩溃。  

**面试关键词**：结构化输出、数据校验、Pydantic 模型。  
## 3 第三题：`execute_sql` 里的 `try/except` 为什么重要，它捕获的错误信息后面会用来干什么。  

> `try/except` 捕获的是 **SQL 无法执行**的错误，比如语法错误、表名或字段名写错。**不是**“结果为空”或“逻辑错误”。  
> 结果为空是正常情况，程序应该正常返回“没有找到数据”，而不是报错。  
> 逻辑错误（SQL 能跑但结果不对）更难发现，需要靠**评估体系**来检查，而不是靠 try/except。  

**为什么这个区分很重要**：因为你的重试逻辑只应该在“SQL 执行失败”时触发。如果结果为空也重试，模型会反复生成同样的 SQL，浪费 token 和时间。  

**面试考点**：  

> 面试官问：“你怎么判断 SQL 执行失败？”  
> 你答：“分三类。第一类，SQL 无法执行，抛异常，触发重试。第二类，SQL 能执行但结果为空，这是正常情况，不重试，直接告诉用户没找到数据。第三类，SQL 能执行也有结果，但逻辑错了，这靠评估体系来发现，不靠 try/except。”
